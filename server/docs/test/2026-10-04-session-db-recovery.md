# 正式环境登录 session 500：数据库进程恢复

## 故障与原因

2026-10-04，正式中心的 `/api/v1/session` 返回 500，页面在登录状态读取阶段显示“数据未能读取”。Server 进程仍在运行，`/health` 返回 200，但 `/ready` 返回 503。

现场确认其 MySQL 协议连接依赖 SQMC04 SeekDB：SQL 端口没有监听，SeekDB 主进程已退出，obshell 管理进程仍在运行。macOS 崩溃报告记录 SeekDB 1.2.0.0 在当日 07:02:53（Asia/Shanghai）发生 `EXC_BAD_ACCESS / SIGSEGV`。应用只读连接诊断得到 `connect: connection refused`，不能把这个故障归为浏览器授权失效。

## 已执行的恢复

- 使用原 SeekDB 二进制、数据目录、SQL 端口和 `cpu_count=4`、`memory_limit=2G` 参数恢复实例；未初始化、重建或迁移数据库。
- 临时前台恢复确认可用后，通过 SIGTERM 正常停止，将同一实例交给 SQMC04 用户 LaunchAgent `com.suqing.seekdb` 管理，使用 `--nodaemon`、`RunAtLoad=true`、`KeepAlive=true` 和 30 秒重启节流。
- 沿用原日志目录、数据库认证与业务配置。obshell 没有重复启动。Server、Web 和 Mac 二进制没有变更，也没有为此重新发版。
- 用户 LaunchAgent 只保证已登录用户的服务管理；不能据此声明未登录启动或整机重启验收完成。退出后自动恢复已配置，未在正式库故意制造崩溃来验收。

## 已有验证结果

接管后的实际进程归属 LaunchAgent，SQL 端口正常监听。正式 `/ready` 返回 200；无授权 Cookie 的 `/api/v1/session` 返回预期的 401，而非 500，页面恢复到授权表单。没有为验收创建新的正式浏览器授权，故不将上述结果描述为已登录浏览器 session 返回 200。

在原正式库上执行现有统计 service 的只读诊断：汇总、机器来源用量、最近 20 个会话详情均成功；这些是实际库读查询结果，不是全仓单元测试或完整 E2E。schema 仍为 v4；新数据库连接读回 `max_allowed_packet=134217728`，此前大快照所需的 128 MiB 设置仍保留。

本地原始证据保存在忽略目录 `.artifacts/session-500-20261004/`，包括连接诊断、恢复后查询结果、服务配置和状态摘要，不提交原始数据、崩溃报告或凭据。提交收尾复用这些结果，不重复运行测试。

## 后续运维与边界

发现 `/health` 正常但业务 500 时，应先检查 `/ready`、真实数据库监听、进程和崩溃报告。SQMC04 当前实例已由 `com.suqing.seekdb` 管理；维护时先检查其状态，不能同时调用旧的直接启动脚本拉起第二个实例。停止或重启共享数据库会影响其他使用者，应先说明影响。

本次恢复解决该次数据库退出造成的登录 session 中断；SeekDB 的段错误触发原因仍未确定，也不将此前其他时段、其他路由的历史 500 全部归为同一原因。升级数据库、迁移存储和修改内核参数不属于本次恢复。

安全自查：生产凭据、权限、Origin/CSRF 与数据库结构未改动，服务配置不含秘密。诊断中误用本地 Cookie 文件格式，异常输出暴露了一条离线演练凭据；已核实它在正式/DEV 库无匹配，并撤销演练库的对应授权，未扩大处理范围。

# SQL 组织与版本交付规范

`docs/sqls/` 是本仓 SQL 文档和文件的统一入口。基底只预置本规范，不携带业务 DDL、examples 建表 SQL、种子数据或默认账号。

## 目录职责

| 目录 | 内容 | 维护方式 |
|---|---|---|
| [schema/](schema/README.md) | 当前完整业务结构，供新环境初始化和结构评审 | 按业务域维护 `<domain>.sql`；实际新增持久化业务时才创建 SQL 文件 |
| [unreleased/](unreleased/README.md) | 尚未随正式版本交付的 SQL | 当前变更先登记在这里，记录目的、前置条件、顺序和验证证据 |
| [releases/](releases/README.md) | 各正式版本交付的 SQL 档案 | 真实版本确定后，按 `vX.Y.Z/` 建目录；无 SQL 的版本不建空目录 |

同一项目不再另设 docs/schema、docs/sql 或另一套 SQL 事实源。`schema` 是当前完整结构；版本目录记录“这个版本交付了哪些 SQL”，二者不能互相替代。

## 新增与更新

1. 先明确目标数据库、表/索引、业务目的及是否有数据写入；复用现有模型和命名。
2. 完整目标结构维护到 `schema/<domain>.sql`；同一改动需要随版本交付的独立 SQL 放 `unreleased/`。不要复制无实际用途的脚本。
3. 文件名使用 `YYYYMMDD_<issue>_<purpose>.sql`；没有 Issue 时省略 issue 段。同日存在依赖时加入 `01`、`02` 序号，并在 README 明确顺序。
4. SQL 文件注释写明用途、适用数据库版本、前置条件、副作用、重复执行行为和失败处理；不要假设 DDL 可以依靠事务撤销。
5. 同步 DO、repository、相关 DTO/VO、设计与配置；结构事实以 SQL 为准，Markdown 不再复制整套 DDL。
6. 未发布清单逐项记录文件、用途、依赖/顺序、归属 Issue、计划版本和已有验证。没有确定的 release 时不填写虚构版本号。

## 正式版本交付

- 只归档本次版本实际包含的 SQL，其他未发布工作继续留在 unreleased；不因文件存在就整体挪走。
- 将选定 SQL 移到 `releases/vX.Y.Z/`，保持文件内容与名称，记录 SHA-256；该目录 README 写明 tag/commit、SQL 顺序、适用前提及对应 schema 文件。
- 归档 README 区分“纳入版本”“已验证”“已执行”。执行记录需有环境、时间、执行人/任务和回读证据链接；没有证据就标记未执行，不从版本目录推断环境状态。
- 同步根 changeLog 的版本条目、unreleased 清单和 SQL 索引；SQL 归档与代码归属于同一真实版本。
- 已发布 SQL 不覆盖、不改写、不删后重建。更正通过新的 unreleased 文件进入后续版本，并明确关联的旧文件与原因。
- 没有 SQL 的版本在发布记录中写“本版本无 SQL 变更”，不创建占位版本目录或空 SQL。

## 新环境与执行

新环境使用目标代码 tag/commit 对应的完整 `schema`，无需逐个重放历史版本文件。初始化记录保留所用版本与文件摘要；不要拿最新工作区 schema 初始化一个旧版本应用。

执行 SQL 是单独的数据库操作：核对目标环境、最小权限、执行顺序和副作用，通过项目约定入口显式执行并回读。构建、归档、发版和应用启动均不因为此目录存在就自动执行 SQL。基底不提供 SQL 执行命令。

SQL 和说明不含密码、Token、完整连接串或真实个人数据。不可恢复的删除、清空和重建操作必须单独表达，不能藏在通用初始化脚本里。
